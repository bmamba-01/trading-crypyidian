# WP-03A.1 — Kiểm toán năng lực Binance USDⓈ-M và SDK

**Ngày kiểm tra:** 2026-11-02

**Phạm vi:** đọc tài liệu công khai và metadata thư viện; không gọi API, không dùng credential, không gửi lệnh; không kiểm chứng Demo bằng kết nối thật.

**Kết luận trạng thái:** kiểm toán tài liệu hoàn tất. Fixture schema/parser, adapter production, kiểm chứng từng capability trên Demo và chốt lựa chọn transport vẫn còn mở.

## Kết luận nhanh

- Tài liệu Binance công bố production REST `https://fapi.binance.com`; môi trường testnet/Demo có REST `https://demo-fapi.binance.com` và WebSocket base `wss://demo-fstream.binance.com`. Binance chỉ nói “most endpoints” dùng được trên testnet. Vì vậy, hỗ trợ riêng cho account, order, Algo Service, listen key và private user stream trên Demo đều **UNKNOWN** cho tới khi có bằng chứng riêng; ma trận dưới đây không suy từ host chung ra khả năng endpoint.
- Lệnh thường thuộc `/fapi/v1/order`; từ 2025-12-09, năm loại conditional `STOP`, `STOP_MARKET`, `TAKE_PROFIT`, `TAKE_PROFIT_MARKET`, `TRAILING_STOP_MARKET` phải đi qua Algo Service. Change Log nêu các loại này bị chặn ở regular order API với `-4120 STOP_ORDER_SWITCH_ALGO`. Phần REST order schema còn liệt kê các type cũ; quyết định routing theo migration/change log hiện hành, không theo danh sách enum tĩnh đó.
- Lịch sử REST không đủ làm ledger lâu dài: order query/all-orders chỉ tối đa 90 ngày, canceled/expired không fill có thể biến mất sau 3 ngày; `userTrades` chỉ truy vấn 3 tháng. Khoảng truy vấn thường tối đa 7 ngày và cần phân trang theo ID/thời gian. Lưu sự kiện/ledger nội bộ là cần thiết; điều này không tự tạo ra tính đầy đủ của snapshot khi có stream gap.
- Gói Python hiện hành là `binance-sdk-derivatives-trading-usds-futures==18.2.0`, phát hành 2026-10-29, MIT, metadata hỗ trợ Python `>=3.11,<3.16` nên tương thích khai báo Python 3.14 của repo. Repo/binance và PyPI author là Binance, nhưng General Info của Binance vẫn mô tả SDK là do partner/user cung cấp, “not officially produced”. README SDK đặt mặc định 3 lần retry REST với backoff 1000 ms; tài liệu không chứng minh retry được phân loại an toàn theo từng thao tác. Chưa thêm SDK.

## Quy ước API, ký và giới hạn

- `NONE`: công khai; `TRADE` và `USER_DATA`: API key + chữ ký; `USER_STREAM`: API key, không yêu cầu chữ ký; `MARKET_DATA`: API key theo bảng security type. API key truyền qua `X-MBX-APIKEY`. `GET` dùng query string; `POST`/`PUT`/`DELETE` nhận query hoặc form `application/x-www-form-urlencoded`. Mốc thời gian là mili giây. Request ký cần `timestamp`; `recvWindow` mặc định 5000 ms, endpoint account hiển thị mức tối đa 60000 ms.
- Rate limit tách theo IP cho request weight và theo tài khoản cho order count. Ghi nhận `X-MBX-USED-WEIGHT-*` và `X-MBX-ORDER-COUNT-*`; khi nhận 429 phải lùi lại, tiếp tục vượt hạn mức có thể dẫn tới 418/IP ban. Trọng số riêng nêu trong bảng dưới đây theo REST catalog tại ngày kiểm tra.
- HTTP 503 phải phân loại theo message: `Unknown error, please check your request or try again later.` nghĩa là trạng thái thực thi **UNKNOWN** vì request có thể đã được nhận; cần kiểm tra user stream/order query trước khi retry. `Service Unavailable.` và `Internal error; unable to process your request. Please try again.` được docs mô tả là request thất bại và có thể retry theo backoff. Không retry mọi 5xx hoặc timeout giống nhau.
- Tham số POST/PUT/DELETE có thể ở query hoặc form body; nếu trùng tham số, query được ưu tiên. Tài liệu tổng quát nói dữ liệu trả theo thứ tự cũ → mới; timestamp millisecond.

### Lịch sử tải bất đồng bộ

REST API order/fill giới hạn thời gian nêu trên không thay thế việc giữ ledger lâu dài. Account REST catalog còn có các nhóm `GET /fapi/v1/order/asyn` và `/order/asyn/id`, `GET /fapi/v1/trade/asyn` và `/trade/asyn/id` để tạo download ID và lấy link lịch sử. Link download có hạn; giới hạn thời gian, quyền, rate và availability trên Demo phải đối chiếu trực tiếp endpoint trước khi triển khai. Tài liệu không bảo đảm các API download có thể lấp event stream gap tức thời.

## Mismatch và cách dùng tài liệu

- **Enum regular-order cũ so với migration mới:** REST schema `/fapi/v1/order` vẫn liệt kê các conditional types, nhưng Change Log ghi chúng đã chuyển sang Algo Service và bị chặn tại regular endpoints. Quy tắc adapter: route năm loại qua Algo Service; fixture cần thể hiện `-4120` tại regular API và các lifecycle khác nhau cho `algoId`/`actualOrderId`.
- **Funding pagination count:** trang `/fapi/v1/fundingRate` ghi `limit` mặc định 100, đồng thời ghi khi không gửi `startTime`/`endTime` sẽ trả 200 record gần nhất. Giữ cả hai chi tiết như docs hiện tại; response thực tế/default phải được xác nhận bằng fixture hoặc Demo trước khi cố định paginator.
- **Demo/Testnet:** testnet host/base được công bố, nhưng từ “most” không xác định API coverage. Không coi SDK có testnet base path là bằng chứng Algo/user-private endpoints hoạt động trên Binance Demo.
- **Snapshot/event recovery:** Binance docs khuyên dùng stream và có REST endpoints để truy vấn snapshot/history, nhưng không cam kết nguyên tử giữa các snapshot, không ghi replay cursor cho stream và cảnh báo REST có thể chậm khi biến động mạnh. Kế hoạch đóng entry gate khi gap và reconcile snapshot + history là suy luận kiến trúc fail-closed; không phải cam kết consistency của Binance.
- **Funding history lookback:** `/fundingRate` nêu phân trang/limit nhưng không nêu retention ceiling trong trang API hiện tại. Cần không gán max history chưa được xác nhận.

## Việc còn mở

1. Thêm fixtures cho request/response và parser theo API schema/version đã chốt; audit này không tạo fixture hay claim test đạt.
2. Xác minh bằng credential Demo explicit-opt-in sau readiness gate rằng account/balance/position snapshots, regular order, Algo order, listenKey và private user events thực sự dùng được; nếu không, ghi capability unavailable thay vì fallback production.
3. Chứng minh phục hồi sau disconnect/expired key bằng snapshot + lịch sử order/trade/algo và đánh giá khoảng thời gian không tra cứu được; không giả định stream replay.
4. Đọc source SDK phiên bản đã pin để xác nhận các private events/Algo schemas và retry classifier; sau đó mới quyết định dependency hoặc HTTP client hẹp trong adapter.
5. API docs hiện vẫn có mâu thuẫn enum regular order / migration; parser fixtures và code phải theo Change Log/migration và lỗi `-4120`, đồng thời cập nhật lại nếu Change Log thay đổi.
